## 2. Objetivo

Especificar la configuración reproducible del entorno inicial local de NexoPyme AI con Python 3.14.10 seleccionado explícitamente, entorno virtual, dependencias justificadas, configuración Django y conexión operativa exclusiva a MySQL 8.x. El bootstrap deberá dejar verificables sus versiones y evidencias sin incorporar funcionalidad de negocio.

## 3. Alcance y exclusiones

**Incluye:** seleccionar e identificar Python 3.14.10; crear y activar `.venv`; declarar dependencias solicitadas con versiones por validar durante el plan; configuración inicial Django; variables de entorno y `.env.example`; protección de secretos; comprobaciones de versión, Django, conexión MySQL, migraciones y pruebas; inicio y verificación del servidor local; documentación de versiones y evidencias.

**Excluye:** módulos de negocio y agentes; despliegue remoto; Redis, microservicios, RAG y bases vectoriales; credenciales reales o inventadas; cambios a `specs/001-productos-inventario`; uso de SQLite para datos operativos. SQLite queda reservado exclusivamente a un futuro checkpointer LangGraph, sujeto a su especificación y configuración posterior.

## 4. Contexto, restricciones y decisiones pendientes

- Normativa: `CONSTITUTION.md` y `AGENTS.md` prevalecen. Se respetan MySQL 8.x como persistencia operativa, ORM/migraciones para acceso a datos, seguridad de secretos, simplicidad y flujo SDD.
- Python 3.14.10 es la selección explícita de esta solicitud; el intérprete bare observado como 3.13.0 no lo sustituye. La disponibilidad local observada vía `py -3.14` es contexto, no evidencia de instalación exitosa.
- Dependencias necesarias para el bootstrap: Django para la aplicación y sus comprobaciones/migraciones; mysqlclient para la conexión Django-MySQL; pytest y pytest-django para las pruebas; Ruff para calidad Python. Pydantic forma parte del conjunto de dependencias declarado del proyecto para validación de datos estructurados; en este bootstrap solo se declara y verifica su compatibilidad, sin implementar modelos ni validaciones de negocio.
- La estrategia definitiva es un único `requirements.txt` con todas las dependencias directas, sin grupos separados de bootstrap e IA ni archivos `requirements-ai.txt` o `*.lock`: Django, mysqlclient, pytest, pytest-django, Ruff, Pydantic, LangChain, LangGraph y `langchain-deepseek` como plugin candidato. Si la verificación de existencia y compatibilidad resulta exitosa, el manifiesto incluirá el plugin; la aprobación humana de esta versión 1.4 aprueba esta decisión condicional. No hay una segunda aprobación ad hoc del plugin. Esto define el contenido del manifiesto, pero no autoriza instalarlo ni implica que toda dependencia deba instalarse en una única operación. T-05 deberá planificar explícitamente qué instalación se realizará; la implementación requiere los gates de aprobación del plan y autorización explícita de implementación previstos en `AGENTS.md` §5. Los manifiestos/locks antiguos preexistentes se identificarán y eliminarán durante T-04, únicamente después de la aprobación humana del plan y las tareas y de la autorización explícita de implementación correspondiente; no se eliminan ahora ni antes de esos gates. No se crearán manifiestos separados ni se sustituirá unilateralmente el paquete candidato.
- La integración candidata `langchain-deepseek` requiere verificar su existencia y documentar la resolución conjunta del conjunto directo para Python 3.14.10 en el entorno temporal efectivamente probado. No se exige una matriz de prueba independiente Windows 10/Windows 11 ni se define una lista cerrada de sistemas operativos soportados. La evidencia se limita al entorno realmente verificado (Windows 10 x64 con CPython 3.14.10) y no implica compatibilidad universal. Si la resolución falla, se observa incompatibilidad o no puede documentarse la resolución/metadata transitiva requerida, T-04 queda bloqueada y se consulta al usuario, sin sustituir el paquete unilateralmente.
- La aprobación de esta especificación no autoriza instalar ninguna dependencia. Para T-05, el plan técnico y las tareas deben contar con aprobación del usuario (aprobación del plan) y la implementación requiere autorización explícita previa conforme a `AGENTS.md` §5; después, la implementación sigue las tareas aprobadas. T-05 debe indicar qué instalación se ejecutará. Las versiones exactas y la compatibilidad se validarán en el plan; no se fijan pins aquí.
- La declaración de dependencias de IA no autoriza activar llamadas a modelos, almacenar estado de checkpointer ni introducir flujos de IA en esta etapa.
- La aprobación de esta especificación, la elaboración del plan y cualquier autorización posterior no deben interpretarse como permiso para instalar, eliminar ni modificar artefactos de dependencias ya existentes antes de que el plan y la aprobación/autorización correspondientes lo permitan. No se presume permiso para sustituir paquetes.
- La limpieza documental, solo después de la aprobación de la especificación, del plan y de la tarea correspondiente, se limita a identificadores personales de cuentas y rutas absolutas del perfil/home: eliminarlos o reemplazarlos por rutas relativas al repositorio. No cambiar nombres propios del proyecto ni datos operativos no personales. El alcance comprende `README.md`, `specs/000-project-bootstrap/spec.md`, `plan.md` y `tasks.md` del bootstrap, y documentación versionada existente. No se limpiarán valores de credenciales porque nunca deben existir en documentación; no registrarlos ni reproducirlos. Se requiere revisión del resultado. `.env.example` se mantiene en alcance solo porque RB-04 ya lo requiere, y debe carecer de credenciales.
- Antes de cualquier conexión MySQL de escritura/migración o ejecución de pruebas con acceso a la base, el usuario/proyecto debe autorizar explícitamente la tupla host, puerto y nombre de base, así como su aprovisionamiento. Es un control independiente y posterior a las aprobaciones SDD; esta especificación no autoriza conexión ni acceso a la base. La tupla autorizada se registra en las tareas sin credenciales.
- La especificación 001 consultada está en borrador y no se modifica ni se toma como aprobada.
- No se crean `plan.md` ni `tasks.md` antes de aprobación humana de esta especificación.
